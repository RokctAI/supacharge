note - how these renders were produced

A widget-test harness (test/render/render_screen_test.dart); zero app code touched. It pumps the real GenericProfilePage after calling this shell's own registerSupachargeProfileSections() - the same function main.dart's generated di-hooks block calls at boot - renders it at 390 logical px (dpr 3) at the page's full content height, and captures the RepaintBoundary to PNG.

The frames are the real ROUTE, not the bare page. StudentProfileRouteView is a Stack of base_sdk's GenericProfilePage plus the floating pill nav (SupachargeNav, Profile slot index 3), and the section list ends in a clearance spacer sized for exactly that nav. An earlier revision pumped GenericProfilePage on its own, which reserved the clearance strip and drew nothing into it - the frame was missing chrome the shipped screen always has.

The data is the SDKs' own demo data, not fixtures written for this page. The test activates a demo session and calls the SDKs' DI registrations in composed-app order; they install their real repositories and base_sdk's DemoGatewayInterceptor answers them from the SDKs' own fixtures. The persona in the identity header comes from signing in through the real AuthRepositoryFacade.login (answered by auth_sdk's api.user.login fixture), persisted through the app's real LocalStorage.setUser.

Real, not simulated: Inter, Montserrat and Roboto are the genuine files Google serves, committed under test/render/fonts/ named by the SHA-256 google_fonts checks them against and handed back through google_fonts' own test seam, which verifies each file's length AND checksum before registering it - so the type is provably the real face and nothing reaches the network. The MaterialIcons and Remix icon fonts come from the Flutter SDK cache and the pub cache. The brand palette is applied through the app's own applyAppBrandColors(), and AppStyle's light/dark tokens are resolved by the real brightness seam.

what these frames deliberately do NOT show

Device history is NOT seeded. The attendance ledger and the library are stores a device accumulates through use - the schedule writes them as lessons are attended, and the attendance-write fixture stores nothing - so a widget test starts with them empty. Seeding them through the real store API is the kit's documented exception; this first adoption takes the default path, so the attendance and per-topic cards show their genuine fresh-device state. That is a truthful frame, not a bug.

Two operator rows (Lesson review, Announcements, Homework queue) are visible because demo mode opens their server gates on purpose - the guided tour previews the admin surfaces. A production student never sees them.

The footer's backend probe and PackageInfo both fail headlessly, so the footer renders its real offline / unknown-version state.

numbering - two keys per wrapped row, on purpose

LmsSchoolCard RETURNS an LmsSettingCard, so the section-id finder and the generic settings-row finder match the same rectangle and the harness's de-duplication keeps exactly one. The section-id spec is ordered first so the durable key normally wins, but the map numbers both spellings (3 for the section id, 4 for the row title) so the page numbers correctly either way and neither number is ever re-issued.

lms.appearance is parked in `retired` rather than deleted. lms_sdk retired the appearance settings row - LmsProfileSections' own doc comment says 'the appearance settings row is retired' and 'the host's top controls row owns the theme toggle now' - so there is no LmsAppearanceCard to find. Its number stays reserved so it can never be re-issued to a different element. The generic lms.setting_row.Appearance spelling keeps its number for the same reason.
